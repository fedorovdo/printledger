# Excel-инвентаризация картриджей

Excel-инвентаризация помогает сравнить расчетный склад PrintLedger с физическим пересчетом картриджей. Preview только проверяет файл и рассчитывает изменения. Apply подтверждает тот же файл и оформляет отличия атомарной пачкой складских корректировок.

## Что считается складом

Склад учитывается отдельно по двум состояниям:

- `new` — новые картриджи на складе;
- `refilled` — заправленные картриджи на складе.

Картриджи, уже установленные в принтерах, хранятся отдельно. Значение «Установлено — справочно» не входит в физический остаток и не участвует в расчете delta.

## Экспорт

Скачать текущий файл можно через:

```text
GET /api/cartridge-inventory/export.xlsx
```

Файл содержит лист `Инвентаризация` и только активные модели картриджей. Технический столбец `ID модели` скрыт, но нужен для надежного обратного сопоставления.

Основные колонки:

- `ID модели`;
- `Производитель`;
- `Модель картриджа *`;
- `Артикул / SKU`;
- `Тип *`;
- `Сейчас — новый`;
- `Сейчас — заправленный`;
- `Новый — факт *`;
- `Заправленный — факт *`;
- `Установлено — справочно`;
- `Мин. остаток`;
- `Комментарий`.

Заполните обе колонки с пометкой «факт». Значения «Сейчас» и «Установлено» предназначены для сверки.

## Пусто не равно нулю

Пустая ячейка в `Новый — факт *` или `Заправленный — факт *` является ошибкой строки. Она никогда не преобразуется в ноль.

Явно введенное число `0` корректно и означает, что при физическом пересчете картриджей этого состояния на складе нет.

Разрешены только целые числа не меньше нуля. Отрицательные, дробные и текстовые значения возвращаются как ошибки preview.

## Сопоставление моделей

Система сопоставляет строку с существующей моделью в следующем порядке:

1. по техническому `ID модели`, если он заполнен;
2. по точному нормализованному названию модели без учета регистра и повторяющихся пробелов;
3. если одинаковых названий несколько, по производителю и/или SKU.

Если ID заполнен, fallback на название не выполняется. Несоответствие существующего ID указанным названию, производителю или SKU блокирует строку ошибкой `MODEL ID MISMATCH`.

Неизвестные модели получают ошибку `UNKNOWN MODEL`, неоднозначные — `AMBIGUOUS MODEL`. Новые модели автоматически не создаются. Одна модель не может встречаться в файле несколько раз: такие строки получают `DUPLICATE MODEL`.

## Preview

Проверить файл без изменения данных:

```text
POST /api/cartridge-inventory/import/preview
Content-Type: multipart/form-data
file=<xlsx file>
```

Preview возвращает текущие и фактические значения, delta, справочное количество установленных картриджей, ошибки, предупреждения и итоговую статистику.

Расчет выполняется так:

```text
delta_new = actual_new - current_new
delta_refilled = actual_refilled - current_refilled
```

Например, если сейчас числится 12 новых картриджей, а фактически найдено 10, preview покажет `delta_new = -2`.

`snapshot_hash` — SHA-256 от модели, фактических и текущих остатков всех корректных строк. Он подтверждает, что склад и Excel-факты не изменились между Preview и Apply.

## Apply

После проверки Preview отправьте тот же XLSX и полученный `snapshot_hash`:

```text
POST /api/cartridge-inventory/import/apply
Content-Type: multipart/form-data
file=<тот же xlsx file>
snapshot_hash=<hash из Preview>
```

Apply повторно читает XLSX, выполняет сопоставление и validation, получает актуальные остатки и пересчитывает preview. Готовые delta от клиента не принимаются.

Если остатки или содержимое фактических колонок изменились после Preview, endpoint возвращает `409 Conflict`:

```text
Остатки изменились после предварительного просмотра. Выполните Preview повторно.
```

Если хотя бы одна строка имеет `status=error`, вся операция блокируется. Частичный Apply не выполняется.

Положительные delta записываются как `correction_plus`, отрицательные — как `correction_minus`. Состояния `new` и `refilled` корректируются независимо, поэтому одна строка может создать до двух транзакций. Строка `unchanged` не создает транзакций.

Вся пачка выполняется в одной транзакции БД с одним финальным commit. При любой ошибке выполняется rollback всей пачки. Конкурирующие штатные операции склада сериализуются общей PostgreSQL advisory-lock, поэтому stock не может измениться между повторной проверкой snapshot и commit Apply.

Для созданных транзакций:

- `reason` — `Инвентаризация из Excel`;
- `comment` содержит имя исходного файла и, если заполнен, комментарий строки Excel;
- `created_by_user_id` берется из текущего authenticated пользователя.

Успешный Apply с изменениями делает прежний snapshot устаревшим. Повторный запрос с тем же hash вернет `409` и не создаст повторные транзакции. Если весь файл `unchanged`, Apply является безопасным no-op и может быть повторен.

## Ограничения

- принимаются только `.xlsx` размером до 5 MB;
- требуется лист `Инвентаризация`;
- строка заголовков может находиться не в первой строке;
- обрабатывается не более 2000 непустых строк;
- полностью пустые строки игнорируются;
- preview не создает складские операции;
- preview не меняет остатки, модели, принтеры, локации или установленные картриджи;
- Apply не создает отсутствующие модели;
- Apply не меняет `CartridgeModel`, `min_stock_level`, совместимости, принтеры, локации и установленные картриджи;
- колонки «Мин. остаток», «Совместимые модели», «Установлено» и «Всего на складе» не являются командами изменения данных;
- остаток никогда не записывается напрямую: используются только `correction_plus` и `correction_minus`.
